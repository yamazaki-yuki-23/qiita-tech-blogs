## はじめに

以前、[MCP Appsで「家系ラーメン検索アプリ」を作ってみた](https://qiita.com/tamakiiii/items/5cc4fd0b49a644a24e23) という記事を書きました。OpenStreetMap のラーメン店データから、家系ラーメンの店を探すアプリです。

「家系かどうか」の判定は、「吉村家」のような店名を並べた手書きのリスト 59 語と、正規表現 1 本で書いていました。実データで動かしたら誤判定が出ていたので、これを [TypeSafe AI](https://docs.typesafe.ai/) に置き換えました。

**店名に空白が入っているだけで、「〜家」で終わるラーメン店 50 件を取りこぼしていました。** リストに語を足しても直りません。原因が語の不足ではなく、店名から屋号を切り出す正規表現そのものにあったからです。

置き換えた結果、判定はこう変わりました。

```
旧（手書きのリスト 59 語 + 正規表現 1 本）
  646 件  confirmed 409 / likely 237

新（TypeSafe AI）
  558 件  confirmed 328 / likely 6 / candidate 224
```

どちらの件数も、アプリが検索結果に表示する店の数です。OpenStreetMap から取ったラーメン店 752 件を判定して、旧は 646 件、新は 558 件が残りました。減った分は、家系以外だと分かって除外した店です。

`confirmed` は家系で確定、`likely` は可能性が高い、`candidate` は「店名だけでは判断できない」です。

:::note warn
**判定の正誤について、先にお断りします**

調べた限り、家系ラーメンに公式な定義や認定制度はありません。この記事で「合っている / 外れている」と書いているのは、すべて店名と OpenStreetMap のタグだけを見て筆者が判断したものです。

そのため、家系なのに外れている店舗や、家系でないのに入っている店舗があります。正確な店舗一覧ではありません。判定ロジックをどう置き換えたかのほうを見てください。
:::

## 1. TypeSafe AI は文章を返さない

TypeSafe AI の Jev は **System One** と呼ばれる種類のモデルです（2026 年 9 月 21 日時点の現行モデルは `jev-1.13.0`）。

ふつうの LLM で分類する場合、プロンプトを送り、JSON で結果を受け取り、その文字列をパースしてスキーマを検証します。形式が崩れていたときの再試行も、自分で書きます。

System One は、そもそも文章を返しません。

> System One models return typed decisions and probabilities rather than generated text.
> ([System One](https://docs.typesafe.ai/concepts/system-one.md))

返ってくるのは型の付いた答えと確率値だけです。自由な文章も推論の過程も返らないので、JSON をパースしてスキーマを検証する処理は要りません。通信エラーやレート制限への対応は、これまでどおり自分で書きます。

聞ける質問は 3 種類あり、プリミティブと呼ばれています。

| プリミティブ | 何を聞くか | 返るもの |
| --- | --- | --- |
| [Noul](https://docs.typesafe.ai/primitives/noul.md) | 条件が成り立つか | 「はい」の確率（0〜1） |
| [Choice](https://docs.typesafe.ai/primitives/choice.md) | 自分で用意した選択肢のどれか | 選ばれた 1 つ + 全選択肢の確率 + 確信度 |
| [Score](https://docs.typesafe.ai/primitives/score.md) | 順序のある段階のどれか | 段階上の位置 + 確信度 |

今回使ったのは Noul と Choice の 2 つです。呼び出しは、公式の JavaScript SDK（`@typesafe-ai/sdk`）からこう書きます。

```js
import { TypeSafeClient, choice, noul } from "@typesafe-ai/sdk";

const client = new TypeSafeClient();

const res = await client.systemOne({
  // 判断材料。名前付きの JSON で渡す
  state: { shop: { name: "横浜ラーメン 田上家", cuisine: "ramen" } },
  // 独立した質問はまとめて投げる。並列に評価される
  questions: {
    is_ramen_shop: noul("Is `shop` a ramen restaurant?"),
    // 選択肢は説明用に 3 つだけ載せている。最終的には 13 個に分けた
    genre: choice("Which ramen genre does `shop` most likely serve?", {
      iekei: "Yokohama iekei: tonkotsu-shoyu broth, thick straight noodles.",
      hakata_tonkotsu: "Hakata or other Kyushu tonkotsu.",
      unclear: "The fields give no usable signal about the genre.",
    }),
  },
});

res.answers.is_ramen_shop.noul  // → 0.97
res.answers.genre.choice        // → "iekei"
res.answers.genre.probabilities // → { iekei: 0.92, hakata_tonkotsu: 0.01, unclear: 0.06 }
```

このコードについて、押さえておきたい点が 3 つあります。

1 つ目は、質問のキー（`is_ramen_shop` など）がモデルに送られないことです。キーは結果を受け取るための識別子でしかないので、聞きたい条件はすべて質問文の中に書きます。

2 つ目は、質問文を英語で書いていることです。公式ドキュメントに次の記述があるからです。店名やタグなどの入力データ（`state`）は、日本語のまま渡しています。

> English is the primary training language and where accuracy is currently best. Other languages, including CJK scripts, are handled but not equally well.
> ([Models](https://docs.typesafe.ai/models.md)：英語が主要な学習言語で精度も一番良い。CJK を含む他の言語も扱えるが同等ではない)

3 つ目は料金です。100 万入力トークンあたり $0.042 で、**課金対象は入力だけ**です（出力は無料）。

## 2. 置き換える前に、実データでの壊れ方を数えた

いきなり書き換えず、まず旧コードが実データで何件間違えているかを数えました。

旧コードの判定は 3 段階です。

1. 除外リストに当たれば対象外
2. 店名で家系を名乗っているか、手書きで登録した家系チェーン名（`吉村家` など）に当てはまれば確定（`confirmed`）
3. どちらでもなければ、「〜家で終わるラーメン店か」を見て可能性あり（`likely`）

```js:scripts/classify.mjs（旧）
const haystack = [name, tags.brand, tags.operator].filter(Boolean).join(" ");
if (EXCLUDE.some((x) => haystack.includes(x))) return null;

if (/家系|横浜家系|よこはま家系/.test(haystack) || matchBrand(haystack)) {
  return "confirmed";
}

const isRamen = /ramen/.test(tags.cuisine ?? "");
// 支店名や括弧書きを落としてから「〜家」で終わるかを見る
const core = name.replace(/[\s（(].*$/, "").replace(/(店|支店|本店)$/, "");
if (isRamen && core.endsWith("家") && !OTHER_GENRES.some((g) => name.includes(g))) {
  return "likely";
}
```

壊れ方は 4 種類見つかりました。

### 2-1. 取りこぼし 50 件：支店名を落とす 1 行が、屋号ごと落としていた

ここから「屋号」という言葉を使います。店名からジャンル名や支店名を除いた、その店固有の名前のことです。`横浜ラーメン 田上家` なら `田上家` が屋号にあたります。

一番影響が大きかったのは、支店名を消すためのこの 1 行です。

```js
const core = name.replace(/[\s（(].*$/, "").replace(/(店|支店|本店)$/, "");
```

前半の `replace(/[\s（(].*$/, "")` は、最初の空白か括弧より後ろを全部捨てます。そのため `横浜ラーメン 田上家` は `横浜ラーメン` になり、「〜家」で終わらないので判定から漏れます。全角スペースの `横浜らーめん　伝家` も同じです。

`cuisine=ramen`（ラーメン店）タグが付いていて、店名も「家」で終わる。それなのにこの処理で漏れていた店が、752 件中 50 件ありました。本来なら `likely` で拾えていたはずの店です。

```
らーめん 粋家 | らーめん 歩家 | 横浜らーめん　伝家 | ラーメン あかね家 |
らーめん たま家 | ラーメン 奥津家 | 横濱ラーメン あさが家 | らーめん 福の家 | ...
```

ただし 50 件すべてが家系ではありません。TypeSafe AI で判定し直すと、検索結果に残ったのは 30 件（確定 7 / 可能性あり 2 / 判定できず 21）でした。残る 20 件は店名から見て食堂や中華料理店とみられるもので、こちらは漏れたままでよいと判断しました。

この正規表現は「店名の前半に屋号が来る」と決め打ちしていました。実際の店名は、そこまで揃っていません。

### 2-2. 残りの 3 種類は、語を足しても根本が直らない

2-1 の取りこぼしが 1 つ目です。残りの 3 種類を順に見ます。

2 つ目は、逆方向の誤りです。家系でないのに家系と判定されていたのは、`塩らーめん嵐家`、`博多ラーメン琥家`、`中華飯店菜家` の 3 件です。家系以外のジャンル名を並べた除外リスト `OTHER_GENRES` に、「塩」「博多」「中華」が入っていませんでした。

3 件なら語を足せば直ります。ただしこの方式では、誤検出が見つかるたびに語を足すことになり、登録漏れがそのまま判定ミスになります。

3 つ目と 4 つ目は、語を足しても直りません。

3 つ目は入力側の誤字です。`横浜家糸ラーメン` という店が、家**系** ではなく家**糸** で登録されていました。人が見ればすぐ分かりますが、`/家系/` の厳密一致では拾えません。

4 つ目はタグの矛盾です。`魂心家` の 1 店舗に、`brand=幸楽苑` という誤ったタグが付いていました。旧コードは除外リストをチェーン名の照合より先に見ていたので、登録してあるはずの `魂心家` が、この 1 タグで除外されていました。

並べると、4 つとも性質が違います。

| 壊れ方 | 語を足して直るか | なぜ |
| --- | --- | --- |
| 支店名を落とす処理が屋号ごと落とす | 直らない | 前提が違う（店名の前半が屋号とは限らない） |
| 家系以外の店を家系と判定する | 個別には直る | 語を足し続ける運用そのものが原因 |
| 入力側の誤字 | 直らない | 表記ゆれではなく打ち間違い |
| 誤ったタグで登録済みのチェーンが除外される | 直らない | 見る順序の設計の問題 |

**足りなかったのは語数ではありません。** 正規表現で屋号を切り出し、例外語を足し続ける方式が、実データの揺れに合っていませんでした。

## 3. 正規表現が判定したかったことを、そのまま質問にする

置き換え作業のほとんどは、「壊れた正規表現が本当は何を判定したかったのか」を言葉にする作業でした。

先ほどの 1 行がやりたかったのは、空白の位置を見ることではありません。**屋号が「〜家」で終わるか**の判断です。文字の位置ではなく単語の役割の問題なので、文字列処理では判定できません。

これをそのまま質問にします。

```js
yago_is_ya: noul(
  // 判断の内容は instructions に書く
  "Ignoring any genre prefix (ラーメン, らーめん, 横浜ラーメン, 中華そば), branch suffix (〜店, 〜本店), and parenthetical, does the shop's own trade name in `shop.name` end with 家 used as a name suffix (屋号)?",
  // どういう場合に true / false かは criteria に分けて書く
  {
    true: "The trade name itself ends in 家, as in 田上家, 吉村家, たから家, ラーメン 千葉家.",
    false:
      "家 only appears inside a word that is not the trade name, such as 自家製麺 (house-made noodles), 麺家 or 中華飯店 used as a generic shop word, or 〜家食堂 / 〜家製麺 where another word follows.",
  },
),
```

何を判断するかは `instructions`（第 1 引数）に、それぞれの答えがどういう場合かは `criteria`（第 2 引数）に分けて書きます。`criteria` は 3 つのプリミティブに共通で、Noul なら true と false の説明、Choice なら選択肢ごとの説明がここに入ります。`shop.name` のようにバッククォートで囲むと、`state` のどのフィールドを指すかを指定できます。

実行すると、確率は低いグループと高いグループにはっきり分かれました。

```:yago_is_ya の確率
0.03  町田商店             0.85  横浜らーめん　伝家
0.05  自家製麺 Ken         0.86  博多ラーメン琥家
0.10  麺家 光              0.89  塩らーめん嵐家
0.13  大黒家製麺            0.95  前田家
0.18  加賀家食堂            0.96  ラーメン 千葉家
```

「自家製麺」「麺家」「〜家製麺」「〜家食堂」は低く出ています。右側の「博多ラーメン琥家」「塩らーめん嵐家」は家系ではありませんが、屋号として見れば確かに「〜家」で終わるので、店名だけを見て答える質問としては期待どおりの値です。家系以外のジャンルかどうかは、別の質問（後述の `genre`）が判定します。

旧コードは「屋号が〜家か」と「家系か」を 1 本の正規表現で同時に見ていたので、どちらの理由で外れたのかが分かりませんでした。**1 つの質問には 1 つの判断だけを持たせる**と、外れた理由を切り分けられます。

この方針で分けた結果、1 店舗につき次の 4 つを投げる形に落ち着きました。

| 質問 | 種類 | 聞いていること |
| --- | --- | --- |
| `is_ramen_shop` | Noul | そもそもラーメン店か |
| `name_declares_iekei` | Noul | 店名で家系を名乗っているか |
| `yago_is_ya` | Noul | 屋号が「〜家」で終わるか |
| `genre` | Choice | どのジャンルのラーメン店か |

## 4. 閾値は、実データの分布を見てから決める

質問を分けたら、次は「確率いくつ以上を家系とみなすか」を決める番です。TypeSafe AI は確率値を返すので、この閾値（しきい値）を実データの分布から決められます。

ただし、最初に決めた閾値ではうまくいきませんでした。

### 4-1. 閾値 1 本だと、0.01 差で結果が分かれる

まず、**店名が家系を名乗っているか**を聞く質問（`name_declares_iekei`）を用意し、「0.9 以上なら確定」という 1 本の閾値で判定しようとしました。

ところが「横浜ラーメン」で始まる店名は、確率が大きくばらつきました。店名の「横浜ラーメン」が家系を指しているのか、横浜という地名を指しているだけなのかが曖昧だからです。

```:name_declares_iekei の確率
0.92  横浜ラーメン 味濱家       0.87  横浜ラーメン 田上家
0.90  横浜ラーメン笑の家        0.86  横浜ラーメン一品家
0.90  横浜ラーメン　弐七家      0.76  横浜らぁめん いちばん家
0.89  横浜ラーメン武蔵家        0.69  横浜らーめん　伝家
0.88  横浜ラーメン 裏武蔵家
```

閾値を 0.9 に固定すると、0.90 の `弐七家` は確定になり、0.89 の `武蔵家` は確定になりません。差は 0.01 しかありません。

しかも、モデルの出力は実行のたびに少し動きます。同じ 30 件を 2 回評価したところ、`佐々木家` の屋号判定（前述の `yago_is_ya`）は 0.87 と 0.84 でした。0.01 差で確定かどうかを決めていると、実行するたびに結果が入れ替わります。

### 4-2. 2 つの質問が一致するかを見ると、揺れが消える

そこで閾値 1 本の微調整はやめ、2 つの質問の結果を組み合わせて判断することにしました。

```js
// 1 つの指標だけで断定してよい確率
export const CONFIRMED_AT = 0.9;
// 単独では足りないが、2 つそろえば断定してよい下限
export const CONFIRMED_PAIR_AT = 0.6;

const iekei = answers.genre.probabilities.iekei ?? 0;

if (answers.name_declares_iekei.noul >= CONFIRMED_AT) return "confirmed";
if (answers.name_declares_iekei.noul >= CONFIRMED_PAIR_AT && iekei >= CONFIRMED_PAIR_AT) {
  return "confirmed";
}
```

0.6 は勘で決めた値ではありません。752 件の分布を見ると、どちらの指標も 0.6 をまたぐ範囲にデータが 1 件もありませんでした。

- `name_declares_iekei` … 0.51 と 0.69 の間に 1 件もない
- `genre` の `iekei` … 0.51 と 0.63 の間に 1 件もない

そこで、ペア判定の閾値を 0.6 にしました。これで、4-1 で挙げた 9 件はすべて確定になります。`伝家` は `name_declares_iekei` が 0.69、`genre` の `iekei` が 0.89。`田上家` は 0.87 と 0.92 です。別の観点から聞いた 2 つの質問がどちらも高い確率を返しているので、多少の揺れでは判定が変わりません。

データの空いている範囲に置けているかどうかは、閾値を動かせば確かめられます。3 つ目の質問である屋号判定（`yago_is_ya`）で試したところ、閾値を 0.4 にしても 0.7 にしても、**752 件のうち判定区分が変わったのは 6 件だけでした。** 動かしても結果がほとんど変わらないこと自体が、その範囲にデータがほとんど無い証拠になります。逆に、少し動かしただけで結果が大きく変わるなら、データが密集しているところで区切っていることになります。

## 5. 「家系ではない」と「判定できない」は別物だった

閾値を決めたあと、今度は判定結果の段階そのものを作り直すことになりました。

旧コードは、「〜家で終わるラーメン店」に当てはまる店をまとめて `likely`（家系の可能性あり）にしていました。ところが、置き換え後に `genre`（Choice）の確率の内訳を見ると、そこには性質の違うものが 2 つ混ざっていました。

```:genre（Choice）が返した確率の内訳（13 個のうち抜粋）
塩らーめん嵐家   shio_or_shoyu=0.71  unclear=0.23  iekei=0.02   ← 家系以外だと分かっている
前田家           unclear=0.93        iekei=0.02                 ← 判断材料が無い
```

前者は検索結果から外すべき店で、後者は「店名からは判断できない」と表示すべき店です。旧コードが両方を `likely` にしていたのは、区別したくなかったからではなく、区別する手段がなかったからです。

そこで、判定結果を「3 段階 + 除外」に作り直しました。

| 段階 | 意味 |
| --- | --- |
| `confirmed` | 家系として確定 |
| `likely` | 家系の確率が高い |
| `candidate` | 屋号は「〜家」だが、名前からは判定できない |
| 除外 | 家系以外だと分かっている |

### 5-1. Choice では、用意していない選択肢は選べない

3 段階に分けたあと、`中華飯店菜家` が `candidate`（判定できない）に残りました。中華料理店なので、検索結果からは外したい店です。

`candidate` は「屋号が〜家」で拾う段階なので、屋号判定の閾値が緩いのだろうと考えました。ところが `yago_is_ya` の閾値をどう上下させても、`candidate` のままでした。

原因は閾値ではありませんでした。`genre`（ジャンル判定）の選択肢に、**中華料理店も食堂も用意していなかった**のです。モデルには選ぶべき選択肢がないので、行き場のない店がすべて `unclear`（判断材料なし）に溜まっていました。そこで選択肢を 2 つ足し、全部で 13 個にしました。

```js
chuka_ryori:
  "A Chinese restaurant (中華料理店 / 中華飯店 / 町中華) that serves ramen alongside fried rice, gyoza and other dishes, rather than a ramen specialist. Note that 中華そば on its own is a shoyu ramen style and belongs under shio_or_shoyu, not here.",
shokudo:
  "A general diner (食堂 / 定食屋) or izakaya that serves ramen among many unrelated dishes.",
```

効果ははっきり出ました。

```:選択肢を足す前 → 足した後
中華飯店菜家      unclear 0.78 → chuka_ryori 0.98   （店名どおり中華料理店へ）
大衆食堂 夢の家                 → shokudo 0.96      （店名どおり食堂へ）
らーめん居酒屋 大野ん家           → shokudo 0.73      （店名どおり食堂・居酒屋へ）
中華そば郷家                    → shio_or_shoyu 0.61（中華そばは一般に醤油系）
```

4 行目の `中華そば郷家` が `chuka_ryori` に落ちないのは、選択肢の説明文に「`中華そば` は `chuka_ryori` に含めない」と書き足したからです。これがないと、名前に「中華」が入っているだけで中華料理店と判定されます。

閾値をいくら動かしても直らなかった問題が、選択肢を足しただけで解決しました。**「判定できない」データが多いときは、閾値ではなく選択肢の不足を疑う。** これが今回いちばん役に立った教訓です。

## 6. うまくいかなかったこと

すべてをモデルで解決できたわけではありません。効かなかった 2 つも書いておきます。

### 6-1. 判断材料が `state` に無い問いは解けない

家系ラーメンには「濃厚」「クリーミー」といった味の傾向があります。これもモデルに判定できるか、Choice で聞いてみました。

チェーン名の対応表では味が決まらず、モデルに答えさせた店が 80 件ありました。その **80 件すべてが同じ `rich` と判定され、確信度は 0.3〜0.8** でした。

```:味を聞いた Choice の答えと確信度
conf 0.37 rich / conf 0.38 rich / conf 0.36 rich / conf 0.44 rich ...
```

選択肢の説明（`criteria`）に「ブランドを特定できなければ unknown と答えよ」と書いても、家系を名乗る店には一律で `rich` を返します。店名とタグだけでは、味を判断する材料がありません。質問文を工夫しても材料は増えません。この質問は削除し、味の傾向はチェーン名の対応表からだけ取ることにしました。

**同じ答えが低い確信度で並ぶときは、質問文ではなく、入力として渡した材料（`state`）の不足を疑う。** これが、ここで得た学びです。

### 6-2. 事実の対応表は、コードに残したほうがよかった

検証を進めるうちに、家系チェーンの `町田商店` が検索結果から漏れました。これは明らかな後退です。

OSM 上のタグは `cuisine: "noodle"`（`ramen` ではない）で、店名も「商店」です。モデルの `is_ramen_shop` は 0.40 で、ラーメン店だと言い切れませんでした。渡した入力がこれだけなら、モデルの判断としては妥当です。

ここで、手書きで持っていた 3 つのリストを、性格ごとに見直しました。

| リスト | 性格 | 旧 | 新 |
| --- | --- | --- | --- |
| `KNOWN_BRANDS`（家系チェーンの登録名） | 定期的に見直す事実の対応表 | 25 語 | 24 語（残す） |
| `EXCLUDE`（家系ではないと分かっている店） | 定期的に見直す事実の対応表 | 12 語 | 13 語（残す） |
| `OTHER_GENRES`（家系以外のジャンル名） | 「〜家で終わる」判定の誤検出を抑えるための語 | 22 語 | 0 語（`genre` が判定する） |

語数が 25 → 24、12 → 13 と入れ替わっているのは、`山岡家` を `KNOWN_BRANDS` から `EXCLUDE` へ移したためです。旧コードは `山岡家` を家系チェーンとして、無条件に確定扱いしていました。ところが 91 店舗すべてで、モデルは家系を選びませんでした（`iekei` の確率は最大 0.33、88 店舗が `unclear`）。山岡家は家系とは別の系統として扱われることが多く、ここは対応表のほうが誤っていたと判断しました。

対応表がモデルに勝つ設計にしておきながら、その対応表をモデルの答えで直したことになります。表の性格を「定期的に見直す事実の対応表」としたのはこのためで、中身を書き換えたのは今回この 1 件だけです。

「吉村家は家系である」は確認済みの事実なので、対応表で管理できます。一方「店名に『博多』が入っていたら家系ではない」は、誤検出を抑えるための推測にすぎず、語を足し続ける運用を招きます。今回削除したのは後者だけです。

チェーン名の対応表をモデルの判定より先に見るようにしたところ、`町田商店` は確定に戻り、2-2 で挙げた `魂心家`（`brand=幸楽苑` の誤タグが付いた店舗）の誤判定も消えました。

```js
// 登録済みのチェーン名はモデルに聞くまでもない。表にある事実が勝つ
if (known.iekeiBrand) return { verdict: "confirmed", ... };
if (known.notIekei) return { verdict: null, ... };
```

公式ドキュメントにも同じことが書かれています。

> Keep known rules, calculations, exact lookups, and execution in code.
> ([How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md))

**すべてをモデルに任せるのではなく、確定した事実の参照と、文脈からの推論を分ける。** これが、今回モデルとコードを分けた基準です。

## 7. まとめ

置き換えの結果です。

| | 旧 | 新 |
| --- | --- | --- |
| 手書きの判定語 | 59 語 | 37 語（事実の対応表だけ） |
| 判定結果 | 646 件 / 2 段階 | 558 件 / 3 段階 |
| 判定の費用 | $0 | $0.045（752 件、1 回） |

得られた学びは 5 つです。

- 語を足しても直らないときは、語数ではなく方式そのものを疑う
- 確率値が返るので、閾値を実データの分布から決められる。データがほとんど無い範囲に閾値を置けば、モデルの出力が少し動いても判定は変わらない
- 「判定できない」データが多いときは、閾値ではなく選択肢の不足を疑う
- 同じ答えが低い確信度で並ぶときは、質問文ではなく `state` に渡した材料の不足を疑う
- 確定した事実の参照はコードに残す。対応表で引けるものをモデルに聞く必要はない。ただし表の中身は定期的に見直す

手書きのリストと正規表現が肥大化して、語を足し続ける運用に追われている箇所があるなら、試してみる価値はあると思います。
