**TL;DR**

- cnfastはclsx + tailwind-mergeをまとめた`cn`関数のドロップイン代替で、tailwind-mergeより平均3.8倍、コンポーネント集約的なコードでは最大7倍速い
- 速さの正体は「全文字列キャッシュ」「トークン単位の記述子キャッシュ」「コンフリクトキーの整数インターン」「SetをInt32Array+世代カウンタで置き換えた衝突追跡」の組み合わせ
- `npx cnfast migrate`1コマンドで既存プロジェクトのインポートを書き換えられる
- 速度改善の恩恵は「再レンダリングが多い画面」「clsx + tailwind-mergeを一緒に使っている」プロジェクトで最も大きい

## はじめに

自分のプロジェクトでは`cn`ユーティリティとして以下のパターンを使っていた。

```typescript
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";

export const cn = (...inputs: ClassValue[]) => twMerge(clsx(inputs));
```

このパターンはshadcn/uiでも採用されており、Tailwind CSSを使うReactプロジェクトではほぼ定番だ。
ここに先日「cnfastが速い」という話を見かけ、気になって調べた。

## cnfastとは

[cnfast](https://github.com/aidenybai/cnfast)は2026年6月に公開されたライブラリで、作者はMillionJSでも知られる[@aidenybai](https://github.com/aidenybai)だ。
GitHubのスターは公開後1週間で975に達している。

位置づけはclsx + tailwind-mergeを内包した`cn`関数の代替実装。
APIは既存の`cn`と完全互換で、出力結果もtailwind-mergeと一致することをfuzzテストで保証している。

```typescript
import { cn } from "cnfast";

cn("px-2 py-1", isActive && "px-4", { "text-red-500": hasError });
// "py-1 px-4 text-red-500"
```

バンドルサイズはgzip後9.43 KBで、clsx + tailwind-mergeの8.45 KBより約1 KB大きい。

## ベンチマーク数値

V8（Node.js / Chrome）でのベンチマーク。

| ワークロード | tailwind-merge | cnfast | 速度 |
|---|---|---|---|
| キャッシュ済み再レンダリング | 2,025 ops/s | 8,709 ops/s | **4.3倍** |
| マージエンジン（コールドスタート） | 1,440 ops/s | 5,411 ops/s | **3.8倍** |
| コンポーネントコーパス | 1,585 ops/s | 6,506 ops/s | **4.1倍** |
| ページレンダリング | 4,249 ops/s | 11,908 ops/s | **2.8倍** |
| ライブデータグリッド | 500 ops/s | 2,185 ops/s | **4.4倍** |

65ワークロードの幾何平均が3.8倍で、113,291件のリアルワールドな呼び出しに対して出力の不一致はゼロ。

## なぜ速いのか

アーキテクチャドキュメントが公開されていたので読んだ。

### 2段階のLRUキャッシュ

tailwind-mergeが全文字列単位でキャッシュするのに対して、cnfastはもう1段追加している。

- **外側キャッシュ（500エントリ）**：入力クラス文字列全体を結果にマップ。tailwind-mergeと同じ粒度
- **内側キャッシュ（4096エントリ）**：個々のトークン（`px-4`、`flex`など）を`ClassDescriptor`（トークンが属するコンフリクトグループのIDなどを持つオブジェクト）にマップ

内側キャッシュが速度に直結する。
異なる2つのクラス文字列が`flex`というトークンを共有している場合、tailwind-mergeは文字列ごとに`flex`をパースして分類するが、cnfastは1回だけ処理してDescriptorを使い回す。

両方のキャッシュともnull-prototypeオブジェクト（`Object.create(null)`）で実装している。
文字列キーの読み取りが`Map.get`より速いためだ。

キャッシュの実装は2世代ローテーション方式で、エントリ単位に退避するのではなく満杯になったら世代ごと入れ替える。
書き込み時のアロケーションがゼロになる。

### コンフリクトキーの整数インターン

Tailwindのコンフリクトキー（`hover:bg`のようなグループ識別子）を文字列のまま比較すると、毎回ハッシュ計算が走る。
cnfastはこれを初出時に整数IDに変換し、以降の比較をint同士で行う。

文字列比較から整数比較に変えるだけでも、ループが数万回回るコールドスタートの処理では差が出る。

### SetをInt32Arrayで置き換えた衝突追跡

マージ処理では「すでに優先度の高いクラスによって上書きされたコンフリクトグループ」を記録する必要がある。
tailwind-mergeの実装はSetを使うため、マージ1回ごとにSetの確保が走る。

cnfastは`Int32Array`と世代カウンタで置き換えた。

```typescript
// 新しいマージを始めるたびに世代カウンタをインクリメントするだけ
currentGeneration = (currentGeneration + 1) | 0;

// キーを「クレーム済み」にするのは配列への書き込みだけ（アロケーションなし）
claimedGeneration[classId] = generation;

// 判定も配列の読み取りだけ
if (claimedGeneration[classId] === generation) continue;
```

Setのインスタンス生成をなくし、スタート時のコストをカウンタのインクリメント1回に減らしている。

### 引数の扱い

`cn`関数の実装は`function`キーワードで書かれており、rest parameterを使っていない。

```typescript
export const cn = function(): string {
  if (arguments.length === 1) {
    const only = arguments[0];
    return typeof only === "string"
      ? twMerge.mergeString(only)
      : twMerge.mergeString(resolveClassValue(only));
  }
  // ...
};
```

rest parameter（`...inputs`）を使うと、V8が呼び出しごとに配列を確保する。
`arguments`オブジェクトは長さとインデックス参照だけに使い、外部に漏らさなければV8がアロケーションを省略できる。

### Tagged templateによるハッシュスキップ

キャッシュヒット時のコストの約半分が「文字列のハッシュ計算」だとプロファイルで確認されているという。
これをスキップする方法がTagged template構文だ。

```typescript
cn`px-2 ${active && "bg-blue-500"}`;
```

Tagged templateの`TemplateStringsArray`はコールサイトごとに同一のオブジェクト参照が再利用される（言語仕様による保証）。
cnfastはこれを`WeakMap`のキーとして使い、文字列のハッシュ計算を完全にスキップする。

V8上で同じコールサイトを繰り返し呼び出すと、tailwind-mergeより4.3倍速い。
ただし`cn(...)`形式はV8がすでに引数をキャッシュしているため、V8上でのtagged templateとの差は1.2倍にとどまる。
V8以外のエンジンでは`cn(...)`のキャッシュが効かないぶん差が広がる。

## 効果が出やすいプロジェクト

cnfastの速度改善は呼び出し回数に比例する。READMEには以下の記述がある。

> `cn` runs once per element, so its cost scales with how much you render. Server-rendering a large page calls it across the whole tree; a client app that re-renders often (data grids, virtualized tables, live dashboards) calls it thousands of times per second, where a faster `cn` keeps frames within budget. On a small or rarely updated page, the saving stays within run-to-run noise.

再レンダリングが多い画面（データグリッド、バーチャライズドリスト、ライブダッシュボードなど）ほど効果が大きく、更新頻度が低いページや小規模なコンポーネントでは誤差の範囲に収まる。

clsxだけを単体で使っているケース（tailwind-mergeなし）も同様で、clsxは元々軽量なのでcnfastへの乗り換えによる体感差は小さい。
恩恵が大きいのはclsx + tailwind-mergeを組み合わせて使っているプロジェクトだ。

## 移行方法

### 既存プロジェクト（clsx / tailwind-merge）

1コマンドでインポートを書き換えられる。

```bash
npx cnfast migrate
```

手動での移行は以下のように変えるだけ。

```typescript
// before
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";
export const cn = (...inputs: ClassValue[]) => twMerge(clsx(inputs));

// after
export { cn } from "cnfast";
```

### shadcn/uiプロジェクト

shadcn/uiのregistryに対応しており、`lib/utils.ts`を自動で書き換えられる。

```bash
npx shadcn@latest add aidenybai/cnfast/cn
```

### clsxのみ使っているケース

cnfastは`clsx`も個別にエクスポートしているので、clsxの代替としてそのまま使える。

```typescript
import { clsx } from "cnfast";
```

ただし前述のとおり、clsx単体の速度改善幅は限定的だ。
tailwind-mergeを併用していない場合は、`cn`パターンへ移行するかどうかをあわせて検討した方がいい。

## 注意点

**出力の互換性**：tailwind-mergeとの出力一致はfuzzテストで保証されているが、プロジェクト固有のtailwind-mergeの設定（`extendTailwindMerge`など）をそのまま移行するには対応が必要になる可能性がある。
カスタム設定を使っている場合は動作確認を丁寧に行う。

**Bunでの数値**：ベンチマーク数値はV8（Node.js / Chrome）のものだ。
BunのエンジンはV8と最適化パスが異なり、speedupの幅が変わる。
プロジェクトの実行環境に応じて確認する。

**まだ新しいライブラリ**：公開から1週間のライブラリなので、エコシステムへの定着やエッジケースの洗い出しはこれからだ。
導入する場合は出力の差分テストを入れておくと安心できる。

## まとめ

cnfastの速度向上は機能削減ではなく、V8の最適化パスを理解したうえでの実装改善で達成されている。
全文字列キャッシュとトークンキャッシュの2段構成、整数インターンによるコンフリクトID、SetをInt32Array+世代カウンタで置き換えた衝突追跡、いずれもアロケーションを削ることへの一貫したこだわりから来ている。

再レンダリングが多い画面を持つプロジェクトであれば、`npx cnfast migrate`で移行コストは低く、出力互換性も担保されているので、試す価値はある。
